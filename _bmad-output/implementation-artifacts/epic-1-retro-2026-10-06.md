## Findings — delivery process

### P1. Verification repeated work without improving coverage

Source: `run-all-tests.sh:37–58`; `package.json:18–20`; Story 1.9 verification notes at lines 291–315;
`AGENTS.md`, Full project check.

One full gate runs build, then E2E's build, then secret hygiene's build: three production builds. Story 1.9 also records
complete reruns after verification-note edits. The repository rule requires the full gate after Markdown edits, making
even final reporting trigger runtime verification again. These are concrete repeated operations, not an elapsed-time estimate.

Disposition: **fix now, proposed**. Build once per verified application/dependency state; reuse that artifact for E2E
and hygiene. Run targeted checks during repair, then one authoritative gate. Validate reporting-only changes with their
own checks. Changing the current repository rule requires owner approval; it has not been bypassed by this retro.

### P2. Review quotas and rebuild routing amplified rework

Source: rendered build `step-04-review.md:29–34,66–99` under
`_bmad/render/bmad-build/mia-frontend-73443eb46a23/6cd94fe1833de1db8700/`;
Story 1.7 review triage at lines 210–218; Story 1.8 review-repair log at lines 120–189.

The workflow demands a size-based finding floor (up to ten) and rejects an empty review. It also prefers `bad_spec`
classification and requires reverting/re-deriving code. Story 1.8 did this after 390 unit/integration and 81 browser tests
had passed. Story 1.7 records 29 findings including 15 false findings. This proves triage and rework volume; it does not
prove that every false finding was caused by the quota. Missing BFCache teardown and clock protection were legitimate fixes.

Disposition: **fix now, proposed**. Permit clean reviews; require a demonstrated defect or acceptance gap. Repair in
place by default. Rewrite only when the existing structure cannot implement the agreed behavior coherently. Group findings
by root cause before dispatching repairs and re-review only affected high-risk interactions.

### P3. Stories included unresolved prerequisites and changing contracts

Source: Story 1.1 lines 133–135, Story 1.2 lines 24–30 and 71–75; Story 1.6 lines 118–121;
Story 1.8 owner decisions; Story 1.9 owner decisions. Git evidence: backend-gap document changed in eight commits,
state machines in seven, and the overarching spec in six.

Localized anonymous entry absorbed session/capability discovery, routing, and logout groundwork. Later stories negotiated
token retention, continuation semantics, URI grammar, profile entry points, and whether lifecycle shielding destroys or
masks secrets. Story titles understated the work. Story 1.8 destruction versus Story 1.9 masking is a particularly important
cross-story boundary, not cosmetic scope.

Disposition: **fix now, proposed**. Resolve transport and lifecycle decisions once before starting a dependent slice.
Name prerequisite work explicitly; put the owner decision in one authoritative place and reference it. Do not make every
story rediscover and copy the same decision across multiple documents.

### P4. Delegation failures became a communication and recovery problem

Source: this conversation's tool results for session `ses_ef452f4e7ffeteGRHUpbOkblpF` (rate limit, interruption, timeout)
and the user turns "Is there progress?", "what is the status?", and "Why does it take so long".

The infrastructure failures were real. The avoidable part was repeatedly waiting/resuming without promptly reporting
what had actually landed, or switching to a bounded recovery plan. The three-block checklist eventually made progress
visible. Redundant confirmation requests also occurred after the user had already approved recommendations and asked for
completion without interaction. Earlier stories' full sessions are unavailable, so this finding is limited to late Epic 1.

Disposition: **fix now, proposed**. Use one visible repair queue with current block, next action, and last verified result.
On a worker failure inspect the diff, make one bounded resume attempt, then choose an available execution path or state the
blocker. Ask again only for a genuinely new product decision. Never imply a worker is still progressing after it has stopped.

### P5. Shared files became integration hotspots

Source: committed snapshots `5679af5`, `6a11549`, `940f038`, `863e09b`, `5ac8fd7`, `e7123e6`, `839220d`.

`sessionController.ts` grew from absent at scaffold to 575 lines after Story 1.2, 1,110 after 1.4, and 1,958 after 1.9.
`App.test.tsx` grew from 17 to 4,816 lines; `e2e/scaffold.spec.ts` from 25 to 2,928. The controller now spans stage
discovery, auth transitions, cross-tab/logout coordination, deadlines, and authenticated/public mutations. This makes
cross-story interaction review more important. Size alone does not establish a duplication defect or justify a rewrite.

Disposition: **accept current structure; prevent further unnecessary growth**. Continue the successful use of separate
reset, invitation, and MFA flow owners and dedicated lifecycle/MFA browser suites. Extract only a demonstrated shared
responsibility; do not spend another MVP cycle decomposing every large file.

### P6. Instruction drift causes repeated decision work

Source: `.agents/rules/security-privacy.md:123–130,200–206` versus Story 1.8's Continue-only decision and Story 1.9's
backend-returned URI grammar. The agent rule still describes ordinary-request idle renewal and the superseded URI form.

Disposition: **fix now, proposed**. Align instruction summaries with owner-approved contracts and use references instead
of parallel specifications. No agent-rule changes were made in this retrospective.

## Findings

The code lenses inspected the full epic diff and focused on story boundaries. The following findings were checked against
the current primary sources. They are proposed remediation, not changes applied during the retrospective.

### C1. Lifecycle recovery can reveal content after the tab is hidden again

Lenses: edge-case-hunter. Sources: `sessionController.ts:421–424,1696–1718`, `SessionProvider.tsx` lifecycle listeners.
`observeLifecycle()` fences only Authenticated state, not an in-progress privacy-shield recovery; deadlines are already
cleared. A delayed explicit Refresh can therefore finish after visibility changes and mount Home while hidden.
The browser exercise reproduced this twice (limitations below).

Disposition: **fix now**. Fence an active recovery on a new lifecycle signal. Regression: delayed discovery/capability
read, hide, release response, assert no protected mount without a later explicit recovery. Prevent recurrence with one
boundary test whenever a later story changes the lifecycle controller.

### C2. Masking removes the deadline needed to destroy retained MFA secrets

Lenses: edge-case-hunter. Sources: `sessionController.ts:1707–1718`; `mfaEnrollment.ts:169–185`.
Lifecycle masking clears the timer and deadlines but retains the MFA secrets. The previously observed expiry can pass
without a destroying transition. This is retained secret lifetime, not a claim that hidden secrets are exposed in the DOM.

Disposition: **fix now**. Keep a conservative destruction deadline while masked without issuing requests or renewing
the session. Test masked retention through expiry. Story 1.9's secret-retention amendment needed a test against Story 1.8's
deadline teardown rather than only tests of each in isolation.

### C3. Retry logout has an anonymous-discovery dead end

Lenses: adversarial and edge-case-hunter (same root). Source: `sessionController.ts:1429–1511`, especially 1442–1447.
After a logout `204` followed by a failed confirmation read, retry discovery can correctly return anonymous. The retry
rejects that stage and remains unconfirmed; repeating follows the same branch.

Disposition: **fix now**. Add contract-aligned recovery using recorded logout success and fresh anonymous confirmation;
do not weaken the accepted reduced logout guarantee. Test `204 → confirmation unavailable → anonymous retry`.

### C4. Verification gates overstate assurance

Lenses: verification-gap. Sources: `package.json:13`, `tsconfig.json:2–5`, `run-all-tests.sh:37`;
`scripts/check-secret-hygiene.mjs:93–109,132–148`.

The advertised typecheck checks an empty solution without building referenced projects. Existing story records disclose
15 application diagnostics and earlier reports disclose tooling errors; neither is certified clean. The hygiene scanner
counts expected failed tests and absence of markers but does not prove that each case reached its intended secret-bearing
checkpoint. An early fixture failure can satisfy the count without exercising the intended failure-report path.

Disposition: **fix now**. Make the actual gate check application and tooling projects, with a deliberately failing type
canary. Require per-case secret-free checkpoint/failure-identity evidence in hygiene; inject an early failure and prove the
gate rejects it. These are fixes to assurance quality, not a request for a larger test count.

### C5. Queued authenticated mutations retain secret-bearing closures until lock acquisition

Lens: adversarial. Sources: `sessionController.ts:365–393`; `mfaEnrollment.ts` verification callback.
The dispatch guard prevents a stale request from sending, but the queued `request.send` closure is nulled only when the
coordinator callback runs or fails. Destroying the owner does not synchronously release that queued payload.

Disposition: **fix now**. Release undispatched payloads on owner/security invalidation without claiming cancellation of
an already dispatched request. Add one held-lock/departure assertion. Do not duplicate the existing coordinator.

### C6. Failed outcome reconciliation leaves old MFA actions available

Lens: adversarial. Sources: `mfaEnrollment.ts:488–495,526–529,581–586`; `features/profile/mfaOutcome.ts:isBusy`.
A failed reconciliation leaves the previous Ready state. `Reconcile failed` is not an in-flight state, so mutation admission
can reuse pre-mutation permissions before the prior outcome is established.

Disposition: **fix now**. Keep the outcome unresolved and offer the explicit reconciliation path; do not admit another
mutation on stale authority. Test ambiguous mutation plus failed read, then deliberate successful recovery.

### C7. Recovery-code departure exception is broader than the initial transfer

Lens: adversarial. Sources: `mfaEnrollment.ts:149–155`; `MfaVerifyRoute.tsx` codes redirect.
The code preserves codes on both verify and recovery-code paths in either direction, not only the initial verify-to-codes
transfer. A programmatic client navigation from codes to verify retained their presentation in the runtime exercise.
Ordinary Back/Forward in a separate exercise destroyed them, so this is not described as a failure of every navigation.

Disposition: **fix now**. Distinguish initial handoff from subsequent departure. Pin the route-owner behavior in a small
regression; do not introduce generic navigation interception.

### Other lens reports: narrower or deferred

- Logout nonce association (`sessionController.ts:1638–1645`) and anonymous CSRF confirmation (`1475–1508`): sources
  show missing explicit checks, but the full guarantee also depends on serialized attempts and discovery's contract.
  **Defer validation into C3's focused review**; do not assert a demonstrated security bypass or add a separate framework.
- Recovery-code binding to a factor replaced on another device (`mfaEnrollment.ts:510–514`): only account and non-null
  active factor are checked. **Defer** until an authoritative enrollment-to-factor binding is established; no cross-device
  reproduction here. This is distinct from the confirmed navigation-lifetime defect.
- Route chunk failure boundaries (`App.tsx`, `ProfileMfaRoute.tsx:88`): lazy/Suspense routes lack a route error boundary.
  **Defer** to shell/resilience work with a failed-chunk exercise; no such failure was exercised here.
- Initial client/server clock skew (`sessionController.ts:1732–1745`): **defer**, already recorded in `deferred-work.md`.
  Do not infer a server-time source or treat rollback tests as clock-synchronization evidence.
- Existing low dependency advisories and manual Safari/AT/print evidence: **defer as already tracked release work**.
  No repeated audit or broad dependency upgrade proposed by this retrospective.

### What worked

The local QR, explicit recovery-code reveal, masking/reveal gate, and single-dispatch enrollment/verification worked in
the bounded runtime exercise. Review repairs added meaningful tests for account and scope changes. Full-gate records
separate skipped tooling and manual evidence from passing automation. Dedicated flow owners and later split browser suites
are useful precedents. Keep these; their existence does not erase the cross-story defects above.

## Behavior verification

Two standalone scripted browser exercises ran against existing `dist/` using an ephemeral local HTTP server and protocol
fakes, not the test runner. External requests were blocked. Command:
`node <harness-temp>/retro-runtime.cjs`. Script and server were removed/stopped afterward; no secrets, screenshots,
traces, or real account data were retained.

Observed: Home mounted; local QR mounted; verify completed with one dispatch; codes absent before Reveal and present
after; visibility hiding removed codes from DOM; Refresh left codes masked; deliberate Reveal restored them. Each run
sent exactly one start and one verify mutation. Delayed Refresh mounted Home while synthetic visibility was hidden in
both runs. Returning visibility reinstated the shield. Navigation findings are qualified under C7.

Environment: macOS 27.0.1 arm64; Node 24.21.0; Playwright 1.63.0; headless Chromium 153.0.8010.12.
HEAD `839220d`; dist index timestamp `2026-10-06T09:59:54.668Z`. Artifact-to-commit provenance was not independently
verified. Visibility signals and clocks were synthetic. This is supporting runtime evidence plus source tracing, not
native BFCache, real-backend, manual assistive-technology, or release certification.

Analysis limits: no complete historical elapsed-work measurement, automated before/after import-graph comparison,
fresh semantic duplication proof, production performance profiling, or backend/manual accessibility evaluation. The
aggregate size measurements are exact committed line counts, not claims that size itself proves poor architecture.

4. **Frontend developer + backend contract owner:** fix C3 logout retry and validate nonce/anonymous-CSRF obligations

5. **Product owner + documentation maintainer:** reconcile stale agent summaries and prerequisite decisions (P3/P6).

Recommended order: agree the lean process; repair gates; execute the two bounded corrective batches; confirm their
cross-story regressions. Do not rerun every review lens on already settled cosmetic or hypothetical findings.

## Acceptance verdict

**rejected** against the declared Epic 1 criteria at this evidence point. All nine story statuses are done, but those
statuses are not proof of epic acceptance. The fresh-authorization/lifecycle behavior and terminal/departure teardown
required by `epics.md:545–568` have the C1/C2/C7 gaps; the explicit logout recovery criterion has C3. C4 also limits the
strength of the previous green-gate claim.

This is a retrospective acceptance judgment, not an instruction to restart the epic or reopen every story. The proposed
response is the bounded corrective work above. The owner's complaint about delivery speed is not authorization to waive
these criteria. A human acceptance override remains available; none has been given. No story statuses are changed here.
