- (decision) Approved sources are mia/docs/product-requirements.md, mia/docs/api.md, the backend PRD and addendum, and the backend architecture spine.
- (decision) Discovery uses the coaching path: product owner and UX facilitator make decisions together rather than drafting unconfirmed assumptions.

- (event) Imported the product owner completed discovery questionnaire as imports/frontend-brainstorming-1.md.
- (decision) MIA must feel safe, patient, and guided. Mistakes are expected and framed as useful for learning; users must not feel controlled, abandoned, overwhelmed, or distracted from their primary task.
- (decision) MIA is not a game. No gamification is used, including for tutoring or exam simulation.
- (decision) Preparation forms provide contextual guidance explaining expected input. Course preparation prioritizes careful, self-explanatory guidance; routine user administration prioritizes speed.
- (decision) The tutor is transparently AI-powered. Generation and other waiting states must visibly communicate that work is continuing so students are not left uncertain.
- (decision) Multi-role accounts use one combined, unified interface rather than separate role workspaces.
- (decision) Release-one visual direction has no existing identity and no dark theme. An age-inclusive mascot is desirable but not yet selected.
- (decision) Interface voice is formal but warm, not colloquial. Student-facing language is simple.
- (decision) Launch UI locales are en-US, de-DE, fr-FR, pt-PT, pt-BR, es-ES, and es-AR. Preferred language controls the whole interface except untranslated backend error details.
- (decision) Course preparation and tutoring are the highest UX priorities. Administration may be merely functional in release one. Student success means completing the second tutoring session without human interface guidance.
- (decision) Consistency is a primary cross-surface requirement. Built-in text-size controls are required because students may not know browser zoom features.
- (decision) Errors use two layers: a localized plain-language explanation and expandable technical details containing the exact HTTP status and complete backend response body. Backend text remains untranslated. Never include headers, cookies, or tokens; escape non-JSON responses as plain text; provide copy functionality with a reminder to review details before sharing.
- (decision) A mentor receives a compact mentoring-request briefing limited to authorized data: minimal student identity, student-written topic, course identity, scheduling context, request status, mentor response, and meeting details. Do not expose tutoring chats, summaries, private material, generated briefs, or an AI-generated student-standing summary.
- (decision) Administrators create inactive courses and assign at least one supervisor. Assigned supervisors prepare and activate courses. A combined administrator-supervisor account may continue directly from creation into preparation within the unified interface.
- (decision) Release one includes the complete mentoring lifecycle as a low-priority, merely functional interface. Student request actions are hidden when unavailable. Supervisor triage and mentor list/detail workflows reuse standard forms and state patterns; UX refinement remains focused on course preparation and tutoring.
- (override) MIA always treats the student as working alone. It provides no special onboarding session and makes no assumptions about a human being present. Any in-person guidance is an external arrangement outside MIA; the interface neither depends on nor represents it.
- (override) MIA is a desktop-browser product optimized for Full HD but does not require or detect physical Full HD resolution. The minimum supported CSS viewport will be validated through prototypes, provisionally around 1024 px. Smaller viewports receive a larger-window advisory rather than a block. Essential security and save actions remain usable, layouts support zoom and built-in text enlargement, and WCAG 2.2 AA is a release requirement.
- (decision) Release one uses one age-inclusive student interface and does not adapt presentation or workflows by age. Age-adaptive presentation based on optional year_of_birth is deferred to the UX backlog.
- (decision) Tutor praise is warm, specific, and evidence-based. It recognizes effort, strategy, correction, and demonstrated understanding; compares with prior work only when supplied history supports it; never invents progress, grades, mastery, or longitudinal knowledge; and avoids repetitive empty praise. Exam simulation reports only measured results and clearly labels limits. The UI adds no gamified celebration.
- (decision) The third critical release moment is resilient tutoring-session recovery: after stream loss, browser closure, or device change, the student immediately understands that the active session and work remain and can resume without duplicate messages, uncertainty, or reliance on browser navigation controls.
- (decision) Tutoring starts with localized static intent choices for homework help, topic practice, explanation, exam preparation, or a free-form question. A choice guides the next step or inserts editable composer text and never submits automatically. Free text always remains available; relevant material selection is optional.
- (decision) Preparation forms use layered guidance: persistent labels and concise helper text carry essential instructions; examples are revealable; tooltips contain supplemental terminology or unusual rules only; validation is colocated and corrective. Long preparation work exposes progress/readiness, preserves draft work, and ends with a readiness review.
- (decision) Course preparation uses a hub with guided sections rather than a linear wizard. It shows each activation prerequisite and distinguishes incomplete, processing, ready-unapproved, and complete states; permits work in a sensible non-linear order; returns users to items needing attention; and explains activation eligibility and the consequences of losing qualifying material.
- (decision) Unified navigation is capability-driven and has no role switcher. It groups Learn, Prepare, Mentor, Administer, and Profile/security; shows only sections with currently authorized actions; preserves visible course and student scope; and lets multi-role users move directly between capabilities. Home surfaces relevant current work without duplicating every section.
- (decision) The tutoring workspace centers transcript and composer, keeps course/session context visible, renders accessible rich text, supports bounded tutor-supplied answer choices plus free text, and exposes only truthful persisted states. It never shows fake percentages, invented processing stages, or hidden model reasoning. Partial and queued content remain distinct; finishing is explicit; navigation avoids accidental confusion; returning routes to the one existing active session.
- (override) Release one does not create dynamic answer buttons from tutor output because the API streams unstructured text. Only frontend-owned static session starters are interactive; tutor replies use the ordinary composer. Structured tutor choices require a future bounded backend schema and are deferred to the UX backlog.
- (decision) Course-wide material presents technical readiness and educational approval as separate text-and-icon states. The workflow is prepare files, process content, review brief, then approve. Approval requires ready file-backed material. Brief editing warns about approval revocation; meaningful changes produce Ready, approval required. Course readiness counts qualifying materials and active courses without one show that existing sessions may finish but new sessions cannot start.
- (decision) Destructive actions scale friction to consequence and state exact scope, preserved data, blockers, irreversibility, and local-only deletion limits. High-consequence account and course deletion require the exact username or course name. Action buttons use precise labels, security resets explain session and password consequences, and removal is shown only after backend success.
- (decision) Release one relies on backend-enforced 30-minute idle and 12-hour absolute session expiry without keepalives or countdowns. On expiry, the frontend clears sensitive in-memory state, returns to a neutral login with a localized explanation, and resumes any still-active tutoring session after reauthentication. Logout remains visible and unsent chat drafts are not persisted in browser storage. Advance expiry warnings are deferred.
- (decision) Localization supports en-US, de-DE, fr-FR, pt-PT, pt-BR, es-ES, and es-AR. Before login, browser negotiation selects the closest locale and a visible selector remains available; after login, preferred language controls UI immediately. Exact matches win, same-language variants use the defined regional fallback, unsupported languages use en-US. UI strings, validation, dates, numbers, and frontend explanations are localized in the preferred time zone; authored content, course material, tutor output, and backend technical errors are not translated. Releases check catalog completeness.
- (decision) The global interface provides device-local Standard, Large, and Extra large text-size choices. Root-relative scaling reflows typography, controls, and spacing; browser zoom remains enabled. Every size meets WCAG 2.2 AA without clipping, hidden actions, or page-level horizontal scrolling at supported desktop viewports. The control is always discoverable and accessible; translated labels are tested at every size.
- (decision) A mascot, if validated, is a restrained age-inclusive brand signature rather than a teacher, fictional friend, or embodiment of the AI tutor. It appears sparingly in welcome, empty, and guidance contexts; never implies emotion, consciousness, monitoring, or human involvement; never becomes a reward mechanic; and is never required for comprehension. Release without one if concepts do not work across audiences.
- (decision) Home is a calm action-and-continuation surface, not an analytics dashboard. It prioritizes an active tutoring session, then scoped course preparation, failed processing, review, mentoring, and operational work by urgency and consequence. Multi-role work is grouped clearly. Home excludes vanity metrics, rankings, streaks, activity feeds, and notification badges; every item links directly to resolution and an empty home remains quiet.
- (decision) Release one uses explicit revalidation rather than continuous global polling: fetch on surface entry, after user mutations, on user return to the tab, on reconnection, and through an explicit Refresh status action. Long-running states show last-checked time and explain work continues after leaving. Tutoring uses SSE. Fresh authorization denial immediately removes stale protected content. Background polling must not keep idle sessions alive.
- (decision) Browser Back, Forward, and Reload remain supported and predictable. In-product navigation provides clear titles, scope, and parent routes; stable URLs and authoritative state recovery make reload safe without duplicate sessions or messages. Active sessions reopen after reload or login. Navigation is intercepted only to prevent loss of unsaved local input, and browser history is never the sole exit.
- (decision) WCAG 2.2 AA keyboard and assistive-technology behavior is a release baseline. Standard keyboard operation reaches every action with no required hidden shortcuts; focus follows reading order and is managed across routes, dialogs, and validation. Streaming is not announced token by token; concise state changes are announced. Rich content is semantic, reduced motion is honored, and no meaning depends on color, hover, motion, sound, or mascot imagery alone.
- (decision) Authentication is one continuous focused journey: username/password, then required MFA, then required temporary-password replacement, with no internal stage jargon or application navigation. Cancel/logout remains available, codes preserve leading zeroes and support paste, completed credential pages are removed from history, and session/CSRF state refreshes after every transition. Public recovery is uniform and staff-only; student recovery remains a supervisor action.
- (decision) MFA activation immediately shows ten recovery codes once on a dedicated surface. It offers Copy all and print-friendly output without automatic download, warns about shared-device and printer risks, requires safe-storage acknowledgement before continuing, warns on navigation, and removes codes from memory and history after departure. Codes never enter logs, analytics, or error reports; loss routes to factor replacement or authorized reset.
- (decision) Staff invitation acceptance captures and removes the fragment token immediately, previews only the invited role, and uses invitation-specific language rather than public sign-up. A guided sequence collects credentials and required profile data, explains password rules without gamification, preserves password bytes, supports reveal, and lets users correct locale/country/time-zone defaults. Acceptance consumption and ambiguous failure are explained safely; post-acceptance behavior follows OpenAPI and does not assume authentication.
- (decision) Learning goals and AI instructions use separate guided multiline plain-text fields, not rich-text editors or new structured persistence. Each explains tutoring impact, offers optional editable templates and examples, shows code-point and byte-limit feedback, preserves line breaks, supports exact read-only preview, warns against secrets and unnecessary personal data, and allows incomplete work to be saved without scoring the supervisor.
- (decision) Material preparation follows draft, review, finalize, and processing. It declares format and limits before upload, supports picker and drag-and-drop, shows per-file progress and failures, forbids mixed formats, preserves recoverable drafts, reviews the file list, and labels the irreversible transition Finalize and process. Processing shows truthful state and last check. The UI disclaims malware scanning and external-link fetching. Student-private material omits approval.
- (decision) Finishing is the only student action that ends a tutoring session. Finish remains visible but secondary, is available only with no generating response or queued message, and requires confirmation that conversation cannot continue. Completion keeps a read-only transcript, starts separately represented summary generation, and later presents strengths, improvement areas, and follow-ups without scores. Failure preserves chat and never implies grading, deletion, or mentor disclosure.
- (decision) Supervisor session review separates active status-only visibility from completed content access. Completed detail shows immutable transcript, material whose content reached the tutor, and a distinct generated review panel. Supervisors may correct summaries and follow-ups but not chat; generated and corrected authorship remain clear; replacement requires confirmation; regeneration appears only when permitted. The interface avoids surveillance and ranking language.
- (decision) Student administration separates Create new student from Add existing student within visible course scope. Supervisors can search the current course roster but have no global student directory. Existing enrollment uses one exact-username field, privacy helper text, and uniform ineligible failure. Temporary credentials are entered with reveal but never retained or copied automatically and are communicated outside MIA. Security, profile, ban, membership, and recovery actions remain distinct.
- (decision) Release-one mentoring uses minimal request list/detail scheduling. It shows only authorized briefing data, renders instants in the viewer time zone with explicit zone context, accepts HTTPS external meeting links, and makes clear MIA neither hosts nor records meetings. Reassignment preserves details; mentor removal warns that future schedule clears and work returns to triage. State actions follow backend rules and use no emergency framing.
- (decision) Release-one administration uses conventional paginated tables and detail pages for accounts, invitations, courses, durable jobs, and audit records. It exposes only supported filters/sorts and no invented totals, distinguishes roles from scoped assignments, keeps consequential actions off crowded rows, provides no bulk destructive actions, and shows safe job status/history. Retry appears only when explicitly supported; tutor and speech recovery remain feature-specific.
- (event) Rendered four visual direction artifacts against Pablo tutoring and supervisor course-readiness samples: Calm notebook, Learning console, Guided current, and Open desk.
- (decision) Visual identity combines Calm Notebook as the governing foundation with Open Desk structural clarity. The product is airy, paper-like, patient, warm, mature, and focused; dense staff and administration surfaces borrow explicit sectional labels and practical hierarchy without adopting Learning Console intensity or Guided Current youthfulness.
- (decision) Tailwind CSS and licensed Tailwind Plus are the UI foundation. MIA uses Tailwind default OS-specific sans-serif fonts throughout and expresses Calm Notebook through palette, spacing, and rhythm rather than a serif font. Playwright runs only on developer macOS devices. Layouts tolerate font-metric variation intrinsically; the Product Owner manually tests other environments and reports findings as bugs or change requests. Cross-platform rendering remains a documented residual risk, not an automated release guarantee.
- (override) MIA uses Tailwind-first inheritance: default Tailwind system fonts, spacing, palette, radii, shadows, and breakpoints, plus the closest licensed Tailwind Plus application shells and component blueprints. Preserve defaults unless a confirmed MIA behavior, accessibility, localization, authorization, or state requirement demands adaptation. Calm Notebook and Open Desk are pattern-selection criteria, not a custom visual recreation. Do not create a custom palette solely for uniqueness; add brand tokens only when a future identity requires them.
- (decision) Selected Tailwind Plus patterns retain useful responsive behavior. Release one optimizes and tests workflows at the default Tailwind lg breakpoint and above with a provisional 1024 CSS-pixel workspace floor. Smaller viewports receive an advisory but are not broken or blocked; essential authentication and safe navigation remain usable. No phone-specific workflows or custom breakpoints are added without evidence.
- (decision) Tutor output uses a strict safe Markdown subset for paragraphs, headings, emphasis, lists, quotes, tables, and code, with locally rendered accessible math. Raw HTML, scripts, frames, forms, media, remote images, and model-defined controls are excluded. Links expose destination and never open automatically. Partial and completed text are sanitized; terminal state re-renders authoritative content; plain text remains fallback; copy and speech use meaningful text.
- (decision) Key journeys use Pablo, a rural Argentinian student on a shared school desktop; Elena, a teacher preparing the first-rollout English course; Rosa, a retired Mexican nurse volunteering as a mentor; and Diego, a technically confident administrator. Their climax beats are independent tutoring completion, confident course activation without a manual, unambiguous external meeting confirmation, and unambiguous completion of consequential administration.
- (decision) Phones may receive SMS codes or run an authenticator app while the MIA interface remains on desktop. Release one has no supported, optimized, or tested phone-browser workflow. Defensive small-viewport behavior keeps essential authentication and logout from being deliberately broken.
- (decision) Release-one Playwright tests run only against Playwright bundled Chromium on developer macOS devices. MIA has no Electron dependency. Current stable Safari is supported through Product Owner manual testing only; findings become bugs or change requests. No Playwright Firefox or WebKit projects are required.
- (decision) Playwright is the confirmed end-to-end testing framework. Release one runs Playwright bundled Chromium only on developer macOS devices. Tests remain browser-independent so Firefox and WebKit projects can be added later. Use isolated contexts and reusable fixtures for multi-role and cross-device scenarios. Do not introduce Cypress or Electron; implementation pins the then-current stable Playwright version.
- (decision) Release one supports current stable Chrome and Edge, plus current stable Safari through Product Owner manual testing. Firefox is outside the supported matrix but is not proactively blocked; reports are change requests unless they reveal a general standards, accessibility, or security defect. Automated E2E remains Playwright bundled Chromium on developer macOS.
- (decision) Frontend application foundation is a client-rendered React 19.2 SPA with strict TypeScript and Vite 8, Tailwind CSS 4.2, licensed Tailwind Plus React components, and Playwright E2E. Echo serves the static production assets. No SSR, React Server Components, Next.js server, or second application backend is introduced. Implementation pins compatible stable patch versions.

- (override) The provisional 1024 CSS-pixel value is an optimization target, not a functionality floor. Every complete process must reflow and remain functional at 320 effective CSS pixels for WCAG 2.2 AA, across all three built-in text sizes. No phone-specific features or phone-support claim is added. Horizontal scrolling is limited to intrinsically two-dimensional labeled regions; the larger-window advisory never reduces functionality.
- (decision) Authentication must meet WCAG 2.2 accessible-authentication requirements: allow password managers, autofill, and paste; use correct autocomplete purposes; expose password-reveal name and state; treat MFA codes as one pasteable text value; and provide TOTP QR plus selectable manual issuer/account/setup information derived locally from the provisioning URI. Test every stage keyboard-only without backend changes.

- (decision) Release-blocking backend contract gap: OpenAPI must provide authoritative discovery of the student's one active tutoring session across courses. - (decision) Release-blocking backend contract gap: OpenAPI must expose a server-authored current-account capability and scope representation sufficient for Learn, Prepare, Mentor, Administer, and Profile/security navigation without policy reconstruction or denial probing. Resource endpoints remain authoritative. The UI defines checking, gained, lost, scope-lost, and no-capabilities states and clears protected content before safe rerouting.
- (decision) Release-blocking backend contract gap: OpenAPI must expose authoritative summary lifecycle and action eligibility for queued, generating, automatic retry scheduled, available, supervisor-corrected, terminally failed, regeneration-eligible, and unavailable states, with required timestamps. Transcript remains independent; regeneration appears only when permitted. Frontend never infers lifecycle from null, time, or a missing generic job.
- (decision) Shared-device cache containment is release-blocking. Backend must apply no-store policy to sensitive authenticated JSON, transcripts, SSE snapshots, mentoring data, private material, source downloads, and generated speech. Frontend prohibits authenticated service-worker/Cache API storage and protected prefetch, authorizes downloads on explicit click, revokes blobs, gates BFCache restoration behind access checking, clears titles/scope/cache on loss, and keeps protected URLs/history content-free.

It warns unsaved input may be lost and offers explicit Continue working through the required auth-session endpoint. No automatic keepalive occurs from typing, open tabs, SSE, polling, or background work. Backend expiry remains authoritative; no exact countdown or absolute-expiry promise is shown.
